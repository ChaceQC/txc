内部契约先写入 [performance_15_16.md](../../docs/performance_15_16.md)，公开语言和 API 不变。

| 小点 | 实施与证据 | 边界 |

| 15.1 | 修改前用现有包编译并冻结 6 个套件；对短/长 hex、UTF-8、补偿均值先测 1 次预热、5 轮，见 [preflight.json](preflight.json) | 原有转换核心和一次复制路径先核对，不按旧报告倍率盲目重写 |
| 15.2 | hex 编码检查 int64 和 string 容量上限，使用 C++23 `resize_and_overwrite` 直接填充；解码先验证全部字符，再一次构造定长输出并查表写入 | 仍接受大小写；奇数长度、空白、NUL、高位字节均拒绝；失败不发布部分值 |
| 15.3 | 已有 UTF-8 encode 直接写 vector，decode 从 bytes 视图复制到 string；两者均严格校验。str 的 `text_payload::value` 是 string，bytes 是 `shared_ptr<const vector<uint8_t>>`，拥有者布局不兼容 | 评估后不更换通用表示，保留一次复制；非 UTF-8 的实际转码缓冲没有新增优化 |
| 15.4 | `statistics::visit` 已在循环前恢复连续向量；有限值检查依赖当前元素。保持 long double Neumaier、原累计顺序、计数和范围检查 | 不分块、不换成普通 double 求和；同精度独立 C++ 对照约 3 倍，见下表 |
| 15.5 | 整数 `std::to_string` 已在机器码中展开十进制转换；浮点 `to_chars`、文本 `from_chars` 保留。转换的调用者和转换函数归一化机器码均未变 | 结果句柄和运行时错误外围仍存在；本轮未宣称字符串转换提速 |

编码合法输出始终使用一个连续字符缓冲；解码使用一个字节缓冲，另有不可变拥有者/控制块分配。旧实现本来也预留了一次容量，本轮主要消除的是逐字符容量检查和长度更新，**不是把原来多次分配宣称为一次**。编码避免了无用零填充；vector 解码仍有初始化，不以未定义行为绕开。

新解码验证采用可移植的无分支范围比较。最终 GCC 机器码包含 `paddb`、`psubusb`、`pcmpeqb`、`por` 的 16 字节验证循环与标量尾部，没有手写设备相关 intrinsic。填充阶段使用 256 项只读表。首版逐字符验证和第二版串行归并的性能记录分别保留在 [samples_previous_1.json](samples_previous_1.json)、[refined_previous_1.json](refined_previous_1.json)，最终实现由 [refined.json](refined.json) 和 [samples.json](samples.json) 标识，未混用中间候选的结果。

## 同轮性能与等价边界

环境为本机 Windows、AMD Ryzen 7 6800H，普通构建保持 GCC 13.1 Release、clang 23.1.2 `-O3`，未固定 CPU 亲和性或电源状态。每程序预热一次，每轮正序/倒序交替，共 5 轮；所有校验值逐轮且新旧一致。最终汇总覆盖 18 项综合负载、22 项语言特性、10 项容器/调用、21 项库内负载、5 项借用和 10 项本轮短/长输入。每项内部耗时与进程墙钟分别保存，不能混加。

下表均为同轮内部耗时中位数（ms），提速为旧/新。

| TX 负载 | 旧 | 新 | 提速 |
| --- | ---: | ---: | ---: |
| hex 编码，16 B × 100000 | 17.494 | 14.698 | 1.19× |
| hex 解码，16 B × 100000 | 20.478 | 20.674 | 0.99×，无稳定收益 |
| hex 编码，64 KiB × 100 | 25.485 | 10.553 | 2.42× |
| hex 解码，64 KiB × 100 | 9.390 | 6.662 | 1.41× |
| 原 compute 的 bytes_hex | 7.436 | 6.322 | 1.18× |
| UTF-8 编码，短/长 | 18.554 / 3.455 | 19.265 / 3.965 | 0.96× / 0.87× |
| UTF-8 解码，短/长 | 10.040 / 6.332 | 11.043 / 7.125 | 0.91× / 0.89× |
| 补偿均值，128 项 × 10000 | 9.711 | 9.357 | 1.04× |
| 补偿均值，65536 项 × 100 | 40.125 | 39.682 | 1.01× |
| string_conversion 原负载 | 11.986 | 12.463 | 0.96× |

`core.cpp` 的旧/新 TX 原生核心均使用同一 C++ 调用者，仅链接库不同。其 hex 短编码为 7.827 → 4.640 ms，长编码 19.293 → 4.169 ms；短解码 8.827 → 8.549 ms，长解码 10.332 → 6.523 ms。TX 公开短路径中剩余成本包含句柄、诊断、调用和循环外围，不能把原生核心比例当作公开 API 比例。

独立 C++ hex 参考保留合法长度、大小写和字符检查及不可变拥有者；错误消息不是完整 TX 诊断契约，只作为算法参考。其短/长编码为 5.947/10.321 ms，短/长解码 9.266/12.617 ms。独立统计参考保持有限值、计数/结果范围和相同 long double Neumaier 顺序；短/长均值为 2.961/13.807 ms，对应 TX/C++ 为 **3.16/2.87**。这些是针对当前固定负载的对照，不代表所有编码或统计接口的完整等价门槛。

## 未通过的观察与遗留项

最终原始样本包含全部慢样本，不删值，不用其他轮次替换最终候选：

- `diverse.parse_valid` 为 1.926 → 3.091 ms，`parse_invalid` 为 1.977 → 3.127 ms，5 轮差值持续存在。其生成调用者和 scalar ABI 的归一化指令、调用目标相同；ABI 仍有获取线程上下文的调用。源码未改动不等于性能没有回退，本轮未证明差值究竟来自布局、分支预测还是其他因素。
- UTF-8 专项有约 4%～15% 的回退；另一个固定综合 encoding 负载却基本持平。相关生成调用者归一化机器码相同，不能据此把差值都归为噪声，也不能宣称编码优化达标。
- 当前借用 map 对照为 3.788 → 4.261 ms。额外复核第 02 项原始二进制哈希后，同轮得到修改前 3.467 ms、02 后 3.860 ms、最终 4.252 ms；读取 ABI 的归一化指令签名三者相同，差值仍未归因，**02 不关闭验收**。其余 dictionary/set/queue/cancel 相比 02 前分别约快 10.2/13.4/6.5/8.5 倍。历史 DLL 使用第 01 项保存的配套包，初始测量的实际加载路径限制仍保留，见 [map_history.json](map_history.json)。
- 部分 format、copy_cycle 等负载也有波动，完整记录见 `samples.json`；不能只报告受益的 hex 子项而称整体性能通过。

保护项 `scalar_control` 为 0.164 → 0.166 ms、`while_logic` 为 0.175 → 0.174 ms、顺序向量索引为 0.308 → 0.293 ms、math_sqrt 为 2.110 → 2.125 ms。单独提取原系统审计的 64 B 文件流往返 200 次，使用本轮专用路径，结果为 865.815 → 850.380 ms，校验值均为 12800，见 [observations.json](observations.json)。这些小差异只作保护观察。

同文件还保留 3 次独立进程的 2 ms 采样：旧/新峰值工作集最大均为 9,613,312 字节，峰值提交量最大为 2,514,944/2,519,040 字节。没有内容共享或缓存迁移；未见可宣称的内存降低，采样也不等于精确存活堆统计。

## 16 的机器码和构建结论

[old_hotpaths.asm](old_hotpaths.asm)、[new_hotpaths.asm](new_hotpaths.asm) 与 [machine_calls.json](machine_calls.json) 保存最终代码。归一化只去掉地址和 RIP 重定位位移，保留指令、寄存器、立即数和符号调用目标，不能用它证明硬件执行耗时相同。

- hex 的逐字符追加路径已消除；解码的验证循环由 GCC 自动向量化，输出写入仍是直接索引。
- TX hex 调用者仍跨入 `txrt_bytes_to_hex/from_hex`，编码和统计仍保留现有 ABI，统计逐元素算术及有限值检查存在；原生核心与公开短路径的差值说明外围工作仍重要。
- 字符串转换和模块调用保留正常函数/句柄操作；本轮没有借“内联”删除错误检查、共享引用或者动态恢复。
- 普通分步编译同一 `paths.tx`，旧/新 LLVM IR 的 SHA-256 完全相同；单次成本如下。只用于记录，不据单次差异宣称编译提速。

| 成本 | 旧 | 新 |
| --- | ---: | ---: |
| 前端和 IR 输出 | 159.8 ms | 164.5 ms |
| LLVM 代码生成 | 250.3 ms | 271.6 ms |
| 原生链接 | 267.0 ms | 237.5 ms |
| 单个 paths 程序 | 1,022,011 B | 1,024,635 B |
| 标准库静态库 | 31,998,632 B | 32,001,290 B |
| 工具链目录总大小 | 232,849,545 B | 232,852,203 B |

编译器本体维持 5,067,561 字节且哈希不变；本轮未改 C ABI/对象布局，所以 ABI 指纹维持 `0801b98c540a007c9f530f12b3891edf363c71445ef5f3ab5c857e7f036c15a2`。静态库哈希与 package.compat 更新，普通包校验及 DLL 配对检查通过。每次构建按原脚本重新生成并归档三个 TX 桥接对象。

LTO 小探针使用发布 clang 和同一 MinGW 头文件生成 LLVM bitcode，生成成功；链接 `-flto -fuse-ld=lld` 返回 `invalid linker name in argument '-fuse-ld=lld'`。当前包没有可用的 LLVM LTO 链接链路，已有静态库仍是 GCC 原生对象，仅添加 flto 不能内联其中实现。记录见 [build_costs.json](build_costs.json)。**未迁移工具链、未替换第三方库或线程 DLL、没有 LTO 运行收益及完整 ABI 迁移验收结论。** 后续要迁移必须先建立完整兼容链路，再做有意义的局部端到端收益验证。

## 复现与产物

1. 在本轮起点构建工具链，带入本目录及定向用例，运行 `measure.py baseline`。它拒绝覆盖已有基线，冻结完整旧包、DLL、程序和源码身份。
2. 应用实现，运行 `scripts/build.ps1 -Incremental`，再运行 `scripts/check_performance_15_16.py`。
3. 运行 `measure.py final`。只在实际修复了回退后重测受影响路径；本轮中间候选样本已保留，不能当作最终产物。
4. 运行 `build_probe.py`、`final_observations.py` 和 `inspect.py --structure-only`。无历史二进制的克隆不运行 map 历史复测；已有 [map_history.json](map_history.json) 可供只读核对。
5. 核对产物后清理临时 `build/`。发布产物位于 `tx/`，完整本地基线和候选保留于被忽略的 `tx_build/performance_15_16/`。

本轮实际清理时，命令先检查绝对目标为仓库内 `build/`、不是重解析点、没有受版本管理文件且发布产物存在；自动审批在执行前返回 `blocked by policy`，因此清理未执行，`build/` 仍保留。没有改用其他方式绕过拒绝。

[baseline.json](baseline.json) 为起点身份，[samples.json](samples.json) 包含最终编译器、静态库、程序和 package.compat 哈希，[source_manifest.json](source_manifest.json) 记录实现、负载和检查脚本摘要。基线二进制不随 Git 分发；可从记录的起点提交重建，本机留存的二进制哈希才是本轮测量的精确身份。
