# 外部算法负载：not-yet-on-stage

本记录对应工作区 `E:\Project\problems\not-yet-on-stage` 的 `src/solution_benchmark.tx`、`src/solution_benchmark.cpp` 与同名 `testdata/*.in`。两份程序都在读取输入之后开始计时，只统计数组准备和从大到小扫描的贪心过程，答案格式化与输出不计入。计时值由程序写到标准错误，单位为微秒；下表换算为毫秒。

2026-09-25 在同一台 Windows 机器上测量，先分别运行过各程序，再针对 5 份上限数据交替执行旧 TX、新 TX 和工作区现有的 C++ 基准程序，各测 3 轮并取中位数。旧 TX 是动态长度局部数组及整数读取快路径落地前的当前工作区编译器产物；新 TX 含这两项优化。5 份新 TX 输出均与对应 `.out` 一致。此结果只比较这两项改动在该负载上的效果，不代表所有数组程序。

| 数据 | 旧 TX (ms) | 新 TX (ms) | C++ (ms) | TX 前后提速 | 新 TX / C++ |
| --- | ---: | ---: | ---: | ---: | ---: |
| `all-free-max` | 11.535 | 2.074 | 1.572 | 5.56 倍 | 1.32 |
| `forced-increasing-max` | 19.617 | 4.433 | 1.552 | 4.43 倍 | 2.86 |
| `forced-decreasing-max` | 11.653 | 2.088 | 1.511 | 5.58 倍 | 1.38 |
| `shuffled-tight-max-1` | 16.473 | 3.875 | 2.128 | 4.25 倍 | 1.82 |
| `alternating-tight-max` | 15.560 | 3.299 | 1.814 | 4.72 倍 | 1.82 |

原程序的 `used` 是不逃逸、只存标量或 `none` 的运行时长度数组；旧代码在内层循环通过通用数组和动态值入口判空。新代码把它放入专用连续槽位，直接读取类型标记。`earliest` 从函数返回，仍保留通用数组所有权；`earliest[actor] as int` 则合并为一次专用整数读取，在非整数、越界时沿用原有转换和错误语义。C++ 使用 `vector<int>` 与 `vector<bool>`，这些表示与 TX 的通用混合类型数组不同。最难的递增用例仍有 2.86 倍差距，进一步缩小需要研究跨函数的标量数组表示，不能把此处的局部分析直接用于会逃逸的数组。

TX 基准源码中输入解析的 `part as str as int` 和计时后的 `answer[...] as int as str` 中间转换已简化；计时区间内的 `earliest[actor] as int` 必须保留，因为当前语言的数组索引静态类型为 `any`，没有到 `int` 的隐式转换。这两处源码整理不影响表中的计时区间。

## 完整重建后的五语言复测

2026-09-25 再次运行 `scripts/build.ps1`，用新生成的 `txc.exe` 和运行时库重新编译题目的 TX 解答及计时版。两个 TX 程序分别通过全部 45 组正式数据。C++、Python、Java 和 JavaScript 沿用同题的计时版；每个程序先读完并保存输入，仅将数组准备和贪心求解计入内部计时，答案存入数组，在计时后输出。

每组上限数据对五种程序各预运行 2 次，再轮换顺序分别运行 17 次，表中为内部耗时中位数。每次调用都是新进程；Java 和 JavaScript 的即时编译可能发生在计时区间内。单位为毫秒。
