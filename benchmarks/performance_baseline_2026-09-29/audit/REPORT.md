# TX 性能审计（2026-09-27）

## 范围与方法

- 在 Windows 11 10.0.26200、Ryzen 7 6800H（8 核 16 线程）上测试当前发行产物。TX 使用随包 clang 23.1.2 的 `-O3`，C++ 使用 GCC 13.1.0 `-O3 -DNDEBUG`，Python 3.12.10，Java 23.0.2。TX 编译器 SHA-256 为 `99C414C45793BAC15AFBAD7B826E91580418B8F5B5800C3F8058B8C270072276`；静态库为 `BBFD14B40EAC3EC344AFF62E006FAE185D06F5B83BA2DD8AA25646DF1DD6C690`。测试前后这两个哈希未变。
- 按 `tx/stdlib/*.txh` 盘点到 37 个公开模块；每个模块至少执行一个 TX 计时负载。另运行已有 22 项语言特性基准，并补充 10 项类型化容器、迭代器和函数值负载。计时为程序内部耗时，不含编译、启动和打印；每项核对校验值。
- 标准库计算与新增语法负载各预热一轮后按交替顺序测 3 轮、取中位数；已有语言特性脚本预热并测 7 轮；已有库基准测 3 轮。系统、HTTP、WebSocket负载也交替运行，文件首轮明显偏高的冷态值未用于结论。
- 基准源码与生成产物在本目录；均位于被忽略的 `tx_build/`。现有编译器、标准库及其他受版本控制的源码未修改。

比较边界：

- `dictionary` 的 C++/Java 对照是整数键容器，TX `dict` 支持混合类型键和值；同样的整数键工作负载下差距真实，但倍率含表示能力差异。下表另有类型化 `map<int,int>` 对照。
- `format` 的 C++ 对照直接拼接已知内容，未实现 TX 的通用格式串语义；`io` 的 Python stderr 缓冲策略不同；`test` 的 C++ 成功断言被 Release 优化掉。这些行不作为“确认 10 倍”证据。
- `statistics` 的 C++/Java 均值对照未执行 TX 的非有限数诊断；`serde` 的 Python/Java JSON 往返未执行 TX 的完整 schema 版本、字段类型和未知字段校验。倍率用于发现热点，不用于声称等价实现。
- `cancel` 的 C++/Python/Java 对照已改为带锁的状态读取；TX 还做动态句柄检查和可选截止时间判断。TX 约为 C++、Java 的 48、54 倍，约为 Python 的 1.6 倍。
- `httpx` 的 Python HTTPX 顶层调用首次测量 100 次约 60.4 秒；该 API 每次创建客户端，具体慢点未继续剖析，故未列入可比栏。Python Requests 在 `requests` 行。HTTP 服务端强制关闭每次连接；Java 重用客户端对象但未重用 TCP 连接。WebSocket 各次重新建连。仅本机回环、小正文、HTTP/1.1。
- `cbor`、`debug`、`error`、`log`、`system` 缺少语义合适的三语言对照，本轮只可确认 TX 负载正常执行，**不能判断其是否超过 10 倍**。CSV 与 XML 也缺少部分语言的同等标准库对照。
- 文件流首轮 TX 约 8.4 秒，随后稳定在约 1.5 秒；相同负载的对照约 0.8–0.9 秒，首轮值应视作系统缓存/文件扫描干扰。进程创建及网络数字受系统状态影响较大。

## 原因定位与建议修改

### P0：把正常路径的源码栈维护移出热循环

`src/backend/llvm/codegen_statement.cpp:305-310` 在每条语句前生成 `txrt_stack_location`。`src/backend/cpp/error_abi.cpp:140-156` 每次访问线程局部栈顶并更新 `std::string file`、行、列；`src/backend/llvm/codegen_functions.cpp:89-104` 还对每次函数调用生成栈压入/弹出。当前 `scalar_control` IR 的 50 万次循环每轮有两处位置更新；旧 IR 的同一循环没有它们。直接链接现行运行时做 100 万次调用，3 轮中位数：`stack_location` 48.0 ms、空 GC safepoint 57.0 ms、`stack_push+pop` 103.6 ms。这个量级与整数循环、sqrt、随机数、类方法和递归的新增耗时相符，是主因的直接证据。

建议先让无错误的算术/控制流块不更新诊断栈；在溢出、除零、索引错误等冷分支更新精确位置后再报错。对可能失败的跨函数调用，保留调用点记录；对 `debug.stack_trace` 等要求实时栈的路径单独保持完整语义。将源文件/函数的静态字面量以非拥有指针或 ID 存在活动栈，真正产生错误时才复制为拥有字符串，可进一步降低剩余调用成本。必须以现有异常位置、嵌套调用栈、析构出错与 `debug` 用例验收。

### P0：对确实无 GC 分配的外部标量调用取消逐轮 safepoint

`src/backend/llvm/codegen_gc.cpp:258-263` 把所有 external 函数判为非 GC-neutral；`src/backend/llvm/codegen_statement.cpp:385-387` 因此在 `math.sqrt` 和随机数调用后每轮生成 `txrt_gc_safepoint`。在 `library_compare_current.ll` 中，100 万次 sqrt 的每轮同时有位置更新和 safepoint；各自直接调用成本约 48 ns 和 57 ns，足以解释大部分 134 ms 的 TX 用时。

建议给外部函数定义可信的“成功路径是否登记 GC 对象”效果属性，先覆盖 `math.sqrt` 等纯标量和已取得上下文的随机数，再按属性省略 safepoint。保持所有可能创建循环对象、执行用户回调或发布引用的调用原有安全点；错误路径仍记录位置。不要简单全局关闭 GC。

### P1：优化静态类型容器和整数运算的生成代码

`src/backend/cpp/container_abi_internal.hpp:22-35` 的每次 typed `map/set/heap/queue` 操作都通过 `std::any_cast<container_handle>`、虚基类存储和 `invoke_checked` 跨 C ABI；`src/backend/cpp/map_i64_abi.cpp` 等已经按静态类型选择入口，仍保留重复动态取存储。可让已经静态确定 `K,V` 的入口持有/借用类型化的共享存储句柄，在从 `any` 恢复时做类型检查，普通读写直接使用具体存储；保留共享别名、GC 登记、缺失键和空容器错误语义。

`features.ll` 的 `vector_index` 每轮调用 `txrt_mod_i64(i,1024)`，尽管除数为常量且非零；它随后才走直接整数向量引用。建议对可证明非零的常量除数生成 LLVM `srem`，对一般除数先守卫零及 `INT64_MIN/-1` 再执行 `srem`，失败跳原错误路径。这样 clang 才能把 `% 1024` 优化成整数指令；向量边界检查仍保留。

### P1：让标量 option 和迭代器 next 避免逐元素堆分配

`src/backend/cpp/iterator_abi.cpp:43-83` 的 `next` 把整数装入 `std::any`，再调用 `txrt_option_new`；`src/backend/cpp/sum_abi.cpp:68-96,151-164` 为每个结果建含两个字段的动态结构和句柄，随后 `.value()` 再复制、拆箱。10 万次读取形成大量可避免的分配。建议为 `option<int/float/bool>` 增加原生 `{present, value}` 表示和直接 next ABI，只有进入 `any`、动态容器或逃逸边界时装箱；复合 `T` 保持现有共享与错误语义。快照迭代器仍须在创建时固定内容。

### P1：消除函数值和 bind 闭包每次调用的克隆

`features.ll` 的函数值循环每轮 `txrt_value_clone → txrt_closure_code → 间接调用 → release`；绑定闭包还在每轮调用 `txrt_closure_parent`、`txrt_closure_capture`、整数拆箱和多次释放。对应实现见 `src/backend/llvm/codegen_expression_calls.cpp:350-390` 与 `src/backend/cpp/closure_abi.cpp`。本地同步调用可借用闭包句柄而不复制；目标在编译期已知且变量未重新绑定时，可直接调用已确定目标并从稳定捕获槽读取标量。仅创建/逃逸边界复制捕获，保持可变复合捕获的共享、`deep_copy`、循环回收及错误传播。

### P2：模块自身的额外成本

- `serde`：`src/stdlib/serde.cpp:246-283` 的 JSON/CBOR 四个入口每次都调用 `serde_parse_schema`；`src/stdlib/serde_schema.cpp:119-122` 又用通用 JSON 解析器重新解析由编译器生成的常量 schema。给每种静态类型/格式生成一次性、线程安全的不可变描述符，或缓存已解析的共享 schema；每次仍做输入、版本、字段、深度和大小检查。本次结构体 JSON 往返 269.8 ms/1 万次，对 Python/Java 约 7.5/7.2 倍，未跨 10 倍，但重复解析是确定的浪费。
- 动态 `dictionary`：`src/backend/llvm/codegen_external_direct.cpp:204-224` 仅为字符串键选专门入口，整数/浮点/布尔键每次 `box_any`；`src/stdlib/dictionary.cpp:64-95` 再从 `std::any` 判别键。为静态键类型加直接 ABI，仍在 `any` 边界和混合键存储处保留类型语义。整数键 contains 的 TX/Java 为 26.4 倍；类型化 `map<int,int>` 仍为 11.6 倍，应先处理 P0/P1 再评估这里的单独收益。
- `cancel.status`：`src/backend/cpp/cancel_abi.cpp:160-169` 每次都解 `std::any` 句柄、复制共享指针并加互斥锁。可评估用原子取消状态和创建后不可变的截止时间供无等待读路径使用，`wait/cancel` 仍按条件变量与同步规则实现；并发下“主动取消先于截止”的状态优先级必须保留。带锁对照的 10 万次状态读为 TX 29.3 ms、C++ 0.61 ms、Java 0.54 ms、Python 17.85 ms。
- `math.sqrt` 还走不可内联的 `txrt_math_sqrt_f64`，每次检查有限值、负数和结果；在 P0 完成后可针对静态数值生成带冷错误分支的 LLVM sqrt 路径，保持 NaN、无穷、负数诊断。随机数使用同一 MT19937_64 时 TX 20 万次约 30.7 ms、C++ 0.33 ms；除 P0 外需检查上下文分支及跨静态库调用，避免牺牲确定的随机序列和参数错误语义。

## 限制与复现

本报告只覆盖每模块一个正常路径，不覆盖所有 API、输入规模、并发、长时内存压力和远程网络；`cbor/debug/error/log/system` 不能据本轮认定“低于 10 倍”。C++ 的极短循环可能被优化器大幅折叠，Java 的进程内 JIT、操作系统文件缓存及基线库的不同检查语义也会影响倍率。报告中的 10 倍是指定负载的观察值，修改后必须重跑等价负载并用错误/别名/GC 用例守住语义。

可直接运行仓库原有 `benchmarks/language_features/run_compare.ps1 -Rounds 7`；本目录的 `compute.tx/.cpp/.py`、`ComputeBench.java`，`features.*`、`system.*`、`legacy.*`、HTTP 与 WebSocket 客户端/本机服务器保存了补充负载。所有四语言计时程序的输出都包含名称、耗时和校验值。测试只生成 `tx_build/` 中的产物；没有修改现有实现。
