# 标准库终态实施顺序

本文是[标准库终态设计](standard_library_complete_design.md)的**实施清单**，替代原有的“标准库扩展规划”全文。原文中的早期批次、过时缺口和分散的实施记录不再作为待办或范围依据。本文按依赖关系列出小工作项；编号表示依赖顺序，不代表版本、可选范围或必须等所有较小编号完成才能推进无依赖工作。十类能力均达到终态设计的[验收矩阵](standard_library_complete_design.md#14-终态验收矩阵)，计划才算完成。

截至 2026-09-28，当前仓库已经有基础容器与算法、`string/encoding/bytes`、文件与系统接口、时间与随机数、JSON/CSV/XML/CBOR/serde、HTTP/WS/Requests 以及一组密码学接口。这些是扩展的起点，不重新作为“待实现”排队；每项开始时仍须核对公开 `.txh`、源码和现有文档，确认实际缺口。第 1 节的公共契约与兼容校验、2.1～2.8、第 3～10 节已落地；第 11 节以后的新增能力仍须逐项验收。

## 执行规则

2026-09-28 对第 9～11 节实现的审查发现 10 项问题（6 项 P1、4 项 P2），问题定位、复现证据和修改记录见[标准库第 9～11 部分实现审查](standard_library_9_11_review.md)。第十三部分复核时，报告中的 R01～R10 均已登记修复；不要把本段的旧状态当作仍未修复的缺口。

1. 每个编号小项先固定具体接口、类型和失败语义；涉及语言规则时先更新[语法说明](syntax.md)与示例，再动编译器。随后交付 `.txh`、对应层的实现、C ABI/LLVM 调用、模块文档和必要的定向验证。
2. 复用现有模块与静态库，不因引入新 API 改变旧函数的排序、编码、错误或共享语义。新旧能力并存时写出迁移示例。
3. 不把“接口已声明”“构建通过”“本机一次往返”单独记为完成。完成记录至少区分代码、构建、定向验证、外部依赖/平台边界和终态验收。
4. 验证按变更直接影响的正常路径、失败路径和资源清理选取；解析器、网络、并发、数据库与密码学的最终专项验证放在相应小项和总验收中，不重复跑与改动无关的大套件。
