# Send/Sync 与跨线程所有权边界

本文固定 2.6 的目标规则及当前实现缺口；[实施清单](standard_library_plan.md)将它拆为“2.6a 静态规则与运行时基础”和“2.6b 最小线程/锁入口的集成验收”。两阶段均通过后才勾选 2.6。

## 实施拆分与完成条件

- **2.6a 静态规则与运行时基础：** 在语义分析中统一判定类型、闭包捕获及不透明句柄的跨线程能力；实现唯一移动、移动后不可用和仍可访问别名的静态拒绝。运行时明确句柄转移与释放、引用计数和循环回收安全点。用正常/非法类型的源码位置诊断及句柄生命周期的定向验证证明这些基础规则；`assert_send/assert_sync` 通过本身不等于完成 2.6a。
- **2.6b 最小线程/锁入口的集成验收：** 在 2.6a 通过后，接入最小 `thread.spawn/join` 和 `mutex<T>` 受控访问路径。用 TX 程序验证唯一移动、原变量与普通别名不可并发访问、闭包捕获约束、锁外访问拒绝、线程错误交付、跨线程释放及循环回收。受锁保护的可变值不能通过普通别名或锁卫士逃逸到锁外。此阶段通过后才能勾选 2.6；第 10 节的完整线程和同步原语仍单独实施与验收。

`Send` 表示一个值可以把所有权交给另一个线程；`Sync` 表示多个线程可按公开 API 同时持有并访问。两者是编译期能力约束，不由运行时 `any` 类型检查或整数句柄值推断。`int/float/bool` 按值传递；`str/bytes` 的载荷不可变，应在跨线程句柄与引用计数安全后同时满足 Send/Sync。`option/result` 仅在其载荷及错误信息的实际表示满足同一能力时继承；闭包须逐个检查捕获值，不能仅凭 `fn(...)` 签名推断。普通 `array/dict/vector/map/set/heap/queue`、可写字段的 struct/class、迭代器默认不满足共享写入所需的 Sync。

编译期断言 `assert_send(value)` 与 `assert_sync(value)` 只接受静态已证明的安全类型，正常求值实参后返回 `void`；不安全类型在实参源码位置报中文错误。这两个断言是类型规则的可验证入口，不执行线程转移或加锁。当前可证明的类型仅为按值传递的 `int/float/bool`；`str/bytes` 虽然载荷不可变，现有 TX 句柄登记与释放尚未证明可跨线程，暂时保守拒绝。其他复合、回调与不透明句柄同样拒绝，待唯一所有权或同步封装的证明接入后扩展。

可变对象跨线程只能走两个明确入口：唯一移动应使原变量不可再读写，并在编译期排除仍可访问的普通别名；同步共享应把对象封装进有锁访问的容器，所有访问必须经过锁卫士。`deep_copy` 可产生独立图，但后续仍能创建别名，因此不能单独充当唯一移动证明。持锁访问不能跨未来的 `await`。闭包跨线程存活必须拥有捕获值；单次同步调用中的临时借用不能转成可逃逸的线程实参。

不透明句柄默认既非 Send 也非 Sync，模块必须逐类声明。当前 `binary_stream/text_stream`、HTTP/WS 连接与监听、后续进程/数据库句柄均禁止直接跨线程；取消令牌的底层状态使用互斥锁和条件变量，但 TX 值句柄跨线程释放安全尚未完成，故不能仅凭底层状态可并发访问就放行。后续 `thread.spawn`、通道和同步容器须调用同一编译期能力判定，不得在各模块各写一套运行时类型白名单。

当前运行时的 `handle_record.references` 和 `internal_references` 是普通计数，句柄登记链表及循环回收节点登记为线程局部数据；跨线程复制/释放一个 TX 值可能在错误的线程注销句柄，循环回收也不能安全扫描正在被另一线程改写的对象图。因此需要先完成 2.6a 的句柄跨线程转移与释放、回收安全点、唯一移动与别名分析，再通过 2.6b 验证同步封装的真实访问路径。此处不把尚未提供的线程接口或单线程取消令牌验证当作并发验收。

**当前进度（2026-09-26）：** `assert_send/assert_sync` 已由语义分析在源码位置检查按值标量；构建通过。`tests/stdlib/send_sync_scalar.tx` 编译运行，`send_sync_alias.tx` 的 `vector<int>` 普通别名及 `send_sync_text.tx` 的 `str` 句柄均在源码位置被静态拒绝。测试复核时收紧了最初放行文本/字节的断言，因为跨线程句柄登记与释放尚未安全。仍无唯一移动或有锁共享的可执行入口，也未验证跨线程句柄生命周期，因此 2.6a、2.6b 与整体 2.6 均未完成。
